# ADR-002 — زیرساخت و هاستینگ

**وضعیت:** ⚠️ نیاز به تصمیم مجدد
**تاریخ:** ۲۸ مرداد ۱۴۰۵
**زمینه:** پیشنهاد اولیه — فرانت روی Vercel، بک‌اند روی سرور ایران

---

## خلاصه‌ی اجرایی

معماری پیشنهادی **دو مشکل جدی** دارد که هر کدام به‌تنهایی برای رد کردنش کافی است:

۱. **Vercel از ایران در دسترس نیست.** کاربران ایرانی با خطای 403 مواجه می‌شوند. یعنی سایت برای مشتری هدف شما باز نمی‌شود.
۲. **حتی اگر باز می‌شد، کندتر می‌بود نه سریع‌تر.** فرانت خارج + API داخل یعنی هر رندر سرور یک رفت‌وبرگشت بین‌المللی.

منطق پشت تصمیم شما درست است — «سرعت برای کاربر» و «پایداری API» هر دو نگرانی‌های واقعی‌اند. اما این ترکیب خاص، هر دو را بدتر می‌کند.

---

## مشکل ۱ — Vercel کاربران ایرانی را بلاک می‌کند

این فرضیه نیست؛ مسئله‌ی جاری و حل‌نشده است.

در انجمن رسمی Vercel، گزارش‌های فعال از کاربران ایرانی وجود دارد:

- **اردیبهشت ۱۴۰۵ (May 2026):** کاربران ایرانی هنگام دسترسی به سرویس‌های میزبانی‌شده روی Vercel خطای **«403 DDoS Mitigation»** می‌گیرند. علت: ترافیک ایران از پشت NAT دولتی عبور می‌کند و Vercel فقط IP های اشتراکی گیت‌وی‌های ایران را می‌بیند، که به‌عنوان ترافیک مشکوک علامت می‌خورند. درخواست رسمی برای whitelist کردن این IP ها ثبت شده و **هیچ پاسخ رسمی‌ای از Vercel داده نشده**.
- **فروردین ۱۴۰۵ (April 2026):** نگرانی درباره‌ی مسدود شدن حساب‌های مرتبط با ایران مطرح شده، باز هم بدون پاسخ رسمی.
- گزارش‌های مشابه به **۱۴۰۳ و ۱۴۰۴** برمی‌گردد. این یک اختلال موقت نیست، یک الگوی چندساله است.

به‌علاوه Vercel خودش قالب آماده‌ی **«Block OFAC-Sanctioned Countries»** را در گالری رسمی‌اش منتشر کرده — یعنی مسدودسازی کشورهای تحریم‌شده بخشی از محصولشان است، نه یک باگ.

**سه ریسک عملی:**

| ریسک                             | اثر                          |
| -------------------------------- | ---------------------------- |
| کاربر ایرانی سایت را باز نمی‌کند | کل کسب‌وکار متوقف            |
| حساب Vercel مسدود می‌شود         | سایت بدون هشدار پایین می‌آید |
| پرداخت هزینه از ایران ممکن نیست  | نیاز به کارت خارجی و واسطه   |

ریسک دوم بدترین است: یک فروشگاه فعال با سفارش‌های در جریان، بدون اطلاع قبلی از دسترس خارج شود.

---

## مشکل ۲ — تأخیر معماری تفکیک‌شده

فرض کنید مشکل اول وجود نداشت. باز هم این معماری کند است.

Next.js با SSR/ISR کار می‌کند (که برای سئوی پارت ۱۰ لازم است). یعنی رندر **سمت سرور** انجام می‌شود:

```
کاربر (تهران)
   ↓ ~۸۰ms
Vercel (نزدیک‌ترین نود: فرانکفورت)
   ↓ ~۹۰-۲۰۰ms  ← ترانزیت بین‌الملل ایران، پرنوسان
API (سرور ایران)
   ↓
دیتابیس
   ↑ همان مسیر برگشت
```

یک صفحه‌ی لیست محصول معمولاً ۳ تا ۴ فراخوانی API دارد (محصولات، فیلترها، دسته‌بندی، شمارش). حتی با موازی‌سازی، **حداقل ۲۰۰ تا ۵۰۰ میلی‌ثانیه فقط شبکه** اضافه می‌شود — قبل از اینکه یک بایت به کاربر برسد.

بند ۱۰.۵۶ برند بوک Core Web Vitals را الزام کرده. این معماری مستقیماً TTFB و در نتیجه LCP را خراب می‌کند.

⚠️ ترانزیت بین‌المللی ایران در ساعات پیک throttle می‌شود و در دوره‌های اختلال شبکه به‌کلی قطع می‌شود. یعنی **کل سایت** به پایدارترین نبودن حلقه وابسته می‌شود.

مقایسه با حالت همه‌چیز در ایران:

```
کاربر (تهران) → CDN داخلی (~۱۰ms) → سرور ایران (~۲۰ms) → دیتابیس
```

---

## نکته‌ی مهم درباره‌ی منطق اولیه

«فرانت را خارج می‌گذاریم تا سریع باشد» یک باور رایج است که از تجربه‌ی سایت‌های **استاتیک** می‌آید. برای یک سایت استاتیک روی CDN جهانی، درست است. اما ArByte:

- SSR دارد (برای سئو، بند ۱۰.۲)
- به‌شدت داده‌محور است (قیمت، موجودی لحظه‌ای)
- مخاطبش ۱۰۰٪ داخل ایران است (بند ۱.۳ — بازار: کل ایران)

برای این پروفایل، **نزدیکی فرانت به بک‌اند مهم‌تر از نزدیکی فرانت به کاربر است**، چون بین فرانت و بک ده‌ها رفت‌وبرگشت اتفاق می‌افتد ولی بین کاربر و فرانت فقط یکی.

---

## گزینه‌های جایگزین

### گزینه الف — همه‌چیز در ایران + CDN داخلی ✅ پیشنهاد من

```
کاربر → ArvanCloud CDN (نودهای داخل ایران)
          ↓
       Next.js (سرور ایران)
          ↓ شبکه داخلی، ~۱ms
       NestJS API (همان دیتاسنتر)
          ↓
       PostgreSQL + Redis + آبجکت استوریج
```

| مزیت                             | توضیح                                    |
| -------------------------------- | ---------------------------------------- |
| بدون ریسک تحریم                  | هیچ وابستگی به سرویس خارجی در مسیر کاربر |
| کمترین تأخیر                     | فرانت و بک در یک شبکه                    |
| پرداخت ریالی                     | بدون نیاز به کارت خارجی                  |
| سازگار با ترب و درگاه‌های ایرانی | بندهای ۶.۳۷ و ۱۰.۶۴                      |
| CDN با نودهای داخلی              | تصاویر محصول از نزدیک‌ترین نود           |

**گزینه‌های عملی:**

- **Liara** — مستندات رسمی استقرار Next.js دارد، تجربه‌ی نزدیک به Vercel، مدل PaaS. برای شروع سریع بهترین است.
- **ArvanCloud** — CDN + ابر + آبجکت استوریج (که بند ۸.۸۹ می‌خواهد) یکجا.
- **پارس‌پک / ایران‌سرور** — VPS معمولی، کنترل بیشتر، کار دستی بیشتر.

**پیشنهاد مشخص:** Liara برای اپلیکیشن‌ها + ArvanCloud برای CDN و آبجکت استوریج.

### گزینه ب — همه‌چیز خارج از ایران

سریع برای بیلد و توسعه، اما: تأخیر بالا برای کاربر ایرانی، ریسک فیلترینگ، مشکل پرداخت، و اتصال به درگاه‌های ایرانی و کاوه‌نگار از سرور خارجی دردسر دارد. **برای فروشگاه داخلی توصیه نمی‌شود.**

### گزینه ج — تفکیک‌شده (پیشنهاد اولیه)

هر دو مشکل بالا را دارد. **توصیه نمی‌شود.**

---

## اثر روی ADR-001

استک فنی (Next.js + NestJS + PostgreSQL) **تغییری نمی‌کند**. هیچ‌کدام به Vercel وابسته نیستند — Next.js روی هر سرور Node.js اجرا می‌شود.

فقط دو نکته در `T-000` باید اضافه شود:

1. `output: 'standalone'` در تنظیمات Next.js — برای اجرای مستقل بدون Vercel
2. Dockerfile برای هر اپ — تا استقرار روی هر میزبانی ممکن باشد

⚠️ **قابلیت‌های اختصاصی Vercel استفاده نشوند:** Edge Middleware، Image Optimization خودکار Vercel، Vercel KV/Blob/Postgres، Analytics. اگر کد به این‌ها وابسته شود، مهاجرت بعداً گران می‌شود. این را به‌عنوان محدودیت در `T-000` اضافه می‌کنم.

---

## نکته‌ی محیط توسعه (این جدا از پروداکشن است)

سرور ایران برای **پروداکشن** درست است، اما برای **بیلد و CI** مشکل دارد: npm، Docker Hub و GitHub از سرور ایران محدودند.

**راه‌حل:** بیلد در محیطی با دسترسی آزاد انجام شود (ماشین خودتان یا یک CI خارجی)، و فقط **ایمیج نهایی** به سرور ایران منتقل شود. یعنی سرور ایران هیچ‌وقت لازم نباشد از رجیستری خارجی چیزی بکشد.

این در `ADR-003` (CI/CD) تفصیل داده می‌شود.
