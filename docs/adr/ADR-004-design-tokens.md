# ADR-004 — توکن‌های طراحی: طراحی به‌جای برند بوک

**وضعیت:** تأیید شده (به‌جز یک مورد باز — بخش «سؤال باز» را ببین)
**تاریخ:** ۳۰ شهریور ۱۴۰۵
**زمینه:** `docs/design/storefront/` (۱۹ صفحه + ۳ کامپوننت پوسته) تحویل داده شد. طبق بند ۱۲.۳ برند بوک، این پوشه منبع حقیقت بصری است و هر جا با برند بوک تفاوت دارد، تصمیم طراحی جایگزین می‌شود — این سند آن تفاوت‌ها را رسماً ثبت می‌کند.

---

## تصمیم

`packages/tokens` (خروجی T-001) بر اساس `docs/design/storefront/README.md` ساخته می‌شود، نه بند ۴ و ۵ برند بوک. مقادیر برند بوک در این سند به‌عنوان مرجع تاریخی نگه داشته شده‌اند تا معلوم باشد چه چیزی عوض شده و چرا.

توکن‌ها **سمنتیک** نام‌گذاری می‌شوند (`--surface-page`, `--text-primary`, `--border-default`, ...) نه بر اساس نام رنگ (`--paper`, `--violet`) — تا افزودن حالت تیره یا تغییر برند در آینده بدون بازنویسی مصرف‌کننده‌ها ممکن باشد.

### توکن‌های جدید که برند بوک اصلاً نداشت

طراحی این‌ها را اضافه کرده — همه معتبرند، مستقیماً از `docs/design/storefront/README.md` گرفته می‌شوند:

`Ink-2 #3D3950` (متن ثانویه/متوسط) · `Line-2 #E0DBF0` (بردر اینپوت/چیپ) · `Line-3 #F0EDF8` (جداکننده‌ی داخلی روی سفید) · `Violet-light #8B6BFF`/`#A88CFF` (روی پس‌زمینه‌ی تیره) · چهار مقدار `Violet-tint` (`#EDE9FA`/`#F4F1FD`/`#F2EFFB`/`#ECE8F9`) · `Violet-tint-border #D6CCF7` · `Cyan-deep #0E7490` · `Cyan-badge-ink #0B3B45` · `Danger-border #E0A3A3` · `Danger-tint #FBEEEE` · `Login canvas #07060B` (فقط صفحه‌ی ورود).

### تأیید Accessibility

کنتراست هر ۸ توکن تغییریافته/جدید روی `#F6F4FC` (پس‌زمینه‌ی اصلی) اندازه‌گیری شد — **همه سطح AA را پاس می‌کنند.** مقادیر تیره‌ترِ Warning و Error در طراحی دقیقاً همان مردودی‌های کنتراست را که در مقادیر برند بوک وجود داشت برطرف می‌کنند؛ این یک بهبود واقعی است، نه صرفاً یک سلیقه‌ی متفاوت.

## Radius — تعارض واقعی

| نقش        | برند بوک §5.12–§5.15                                           | طراحی                                                                                                 | نتیجه                              |
| ---------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------- |
| مقیاس پایه | 4/8/12/16/20/24px                                              | Card 22px، Large card/section 26px، Panel 18–20px، Inner tile 12–16px، Chip 10px، Icon button 12–13px | **مقیاس متفاوت — طراحی برنده است** |
| Button     | ۱۰–۱۲px، **صریحاً نباید Pill پیش‌فرض باشد** مگر Chip/Tag/Badge | `999px` (Pill کامل) برای دکمه‌های اصلی                                                                | **تعارض مستقیم — طراحی برنده است** |

بند ۵.۱۳ برند بوک صراحتاً دکمه‌ی Pill پیش‌فرض را رد کرده بود؛ طراحی این تصمیم را عوض کرده. طبق بند ۱۲.۳، این یک override رسمی است، نه یک لغزش — دکمه‌های اصلی در `apps/web` باید Pill (`radius: 999px`) باشند.

## Breakpoints — تعارض واقعی

| برند بوک §5.7                                                                  | طراحی                                               |
| ------------------------------------------------------------------------------ | --------------------------------------------------- |
| Mobile < 640px، Tablet 640–1024px، Desktop 1024–1440px، Large Desktop > 1440px | Mobile ≤ 767px، Tablet 768–1023px، Desktop ≥ 1024px |

برند بوک خودش گفته بود «مقادیر نهایی می‌توانند در زمان توسعه اصلاح شوند» — طراحی همین کار را کرده. مقادیر طراحی (۷۶۷/۱۰۲۴) در `packages/tokens` و پیکربندی Tailwind استفاده می‌شود، مخصوصاً چون طراحی صراحتاً می‌گوید «۹۰٪ ترافیک موبایل است؛ موبایل حالت اصلی است».

## Spacing — بدون تعارض، با یک نکته‌ی اجرایی

هر دو منبع روی مقیاس ۴px پایه توافق دارند (قاعده‌ی غیرقابل‌مذاکره‌ی #۳). اما طراحی برای ریتم بخش‌ها و padding کارت از مقادیر fluid با `clamp()` استفاده می‌کند (مثلاً `clamp(18px, 3vw, 26px)`) که کران‌های آن همیشه دقیقاً روی مقیاس ۴px نیستند (۱۸ و ۲۶ مضرب ۴ نیستند).

**قاعده‌ی اجرا در T-001:** کران‌های `clamp()` به نزدیک‌ترین مقدار مقیاس ۴px snap می‌شوند (۱۸→۱۶، ۲۶→۲۸) مگر جایی که این تغییر رفتار بصری محسوسی ایجاد کند — در آن صورت مقدار طراحی عیناً نگه داشته می‌شود و اینجا یادداشت می‌شود. رفتار fluid (`clamp`/`vw`/`vh`) خودش حفظ می‌شود؛ فقط کران‌های ثابتش با مقیاس هماهنگ می‌شوند.

## Shadow — بدون تعارض

برند بوک (§3.26، §9.69) فقط اصل کیفی «Shadow باید Minimal باشد، از سایه‌های سنگین پرهیز شود» را گفته، بدون مقدار مشخص. مقادیر طراحی (`0 12px 34px rgba(23,21,31,.08)` تا `0 22px 50px rgba(23,21,31,.14)`) دقیقاً همین اصل را با alpha پایین (۰.۰۶–۰.۱۸) پیاده می‌کنند. طراحی مستقیماً استفاده می‌شود.

---

## Typography — بدون تعارض، فقط تکمیلی

خانواده‌ی فونت (Estedad) و جهت (RTL) در هر دو یکسان است. برند بوک مقیاس دقیق تایپوگرافی تعیین نکرده بود؛ طراحی این خلأ را با مقیاس کامل (hero/h2/sub-head/body/caption، همه با `clamp()`) و قواعد موبایل (حداقل 16px روی input برای جلوگیری از zoom خودکار iOS) پر می‌کند. اینها مستقیماً به `packages/tokens` منتقل می‌شوند.

## سؤال باز — Success و Info

برند بوک بند ۴.۲۰ یک سیستم Status چهاربخشی الزام کرده (Success سبز / Warning نارنجی / Error قرمز / Info آبی) که «باید در Frontend و Backend یکسان باشد». طراحی فروشگاه (۱۹ صفحه) **هیچ‌جا از سبز یا آبی استفاده نکرده** — حالت‌های مثبت (ذخیره‌ی موفق، افزودن به سبد) با پرشدن Violet-tint + آیکون/متن نشان داده می‌شوند، و نشانگرهای «زنده»/موجودی با Cyan.

این می‌تواند دو معنی داشته باشد:
۱. طراحی عمداً Success/Info سبز و آبی را از کل سیستم حذف کرده (بنفش/فیروزه‌ای جایگزین شده‌اند)، یا
۲. این ۱۹ صفحه صرفاً به آن‌ها نیاز نداشتند، و Success/Info سبز/آبی برای بخش‌هایی که هنوز طراحی نشده‌اند (مخصوصاً **پنل ادمین** — وضعیت سفارش، Notification، Alert) لازم می‌مانند.

**پیشنهاد من:** گزینه‌ی ۲. چون بند ۴.۲۰ صراحتاً هماهنگی Frontend/Backend را خواسته و پنل ادمین (که هنوز طراحی ندارد) به احتمال زیاد به Status رنگی واضح‌تر از حد قابل‌قبول در فروشگاه نیاز دارد، `--status-success` (`#16A34A`) و `--status-info` (`#2563EB`) را به‌عنوان توکن‌های رزرو در `packages/tokens` نگه می‌دارم — اما در `apps/web` مصرف نمی‌شوند مگر جایی که طراحی صراحتاً بگوید. اگر قالب ادمین که می‌آید (`docs/design/admin/`) الگوی دیگری نشان داد، این تصمیم به‌روزرسانی می‌شود.

اگر با این پیشنهاد موافق نیستید، بگویید.

## باگ جداکننده‌ی هزارگان قیمت

فایل‌های طراحی در تابع نمونه‌ی `money()` از `٫` (U+066B، جداکننده‌ی **اعشار** عربی) به‌عنوان جداکننده‌ی هزارگان استفاده کرده‌اند (۴۶ مورد در فایل‌های `pages/*.dc.html`، همه در نمایش قیمت). جداکننده‌ی درست هزارگان فارسی `٬` (U+066C) است.

توجه: همه‌ی `٫`های فایل‌ها اشتباه نیستند — مواردی مثل «۳٫۶ کیلوگرمی» یا «Wi-Fi ... ۲٫۵ گیگابیت» اعشار واقعی‌اند و درست‌اند. فقط جداکننده‌ی هزارگان در قیمت‌ها (`۲۸۹٫۵۰۰٫۰۰۰`) اشتباه است.

فرمتر واقعی در `packages/contracts/src/format/money.ts` با `٬` درست ساخته می‌شود (بخشی از زیرساخت T-001/T-005، نه یک مدل داده‌ای).
